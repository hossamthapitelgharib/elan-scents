# تدقيق الحالة وخطة التنفيذ

**تاريخ التدقيق:** 14 أكتوبر 2026
**المستودع:** `hossamthapitelgharib/elan-scents`، الفرع `main` عند الالتزام `54bec96` وقت الفحص
**مشروع Supabase:** `supabase-blue-blanket` (`sbgdtuqfrnfeggkwqtrw`)
**الغرض:** نقطة انطلاق موثّقة للمشروع؛ ليست ادعاءً بأن جميع لوحات المنصة والمتاجر اكتملت.

## خلاصة تنفيذية

- **فصل اللوحات والصلاحيات موجود إلى حد كبير:** واجهة «طلباتي» منفصلة عن «لوحة العملاء»، وقوائم العملاء والتحليلات والتفاصيل الفردية محمية بخادم يتطلب دور `platform_admin`.
- **سجل الزوار والعملاء موجود:** هوية متصفح عشوائية pseudonymous، سلة زائر، سجل جلسات، أحداث منتجات، إحصاءات مجمعة للزوار، وسلة العميل المسجل وأحداثه.
- **الأقسام الأربعة للترتيب موجودة للطرفين:** مشاهدة، ظهور منتج في البحث، إضافة للسلة، وحذف/تقليل منها؛ والترتيب تنازلي حسب العمليات مع كاسرات تعادل مستقرة.
- **تحسين أُنجز في هذه المهمة:** لوحة التفاصيل الفردية أصبحت تستخدم لقطة المنتج التاريخية الكاملة في سلال الضيف والعميل وأحداث النشاط، وتُبقي الحدث ظاهرًا عند غياب سجل المنتج الحالي. طُبّق ترحيلها على Supabase وطابق رقم الملف مع الإصدار المسجل.
- **الاكتمال الشامل لمتطلبات المتاجر/المنصة غير قابل للإعلان بعد:** المستخدم قال إن تفاصيل كثيرة ستحدد مستقبلًا؛ يجب تحديد تلك المتطلبات، ومراجعة قاعدة المتاجر وواجهاتها بندًا بندًا قبل اعتبارها مكتملة.
- **تنظيم المستودع يحتاج تحسينًا تدريجيًا:** ملفات الواجهة وبعض صفحات لوحات الإدارة في الجذر، مع تقسيم مفيد قائم إلى `api/`, `lib/`, `railway/`, `editor/`, `supabase/`, `tests/`, `reports/`. لا يُنصح بنقلها قبل خريطة المسارات واختبارات منع الانحدار.

## مصفوفة الحالة بحسب طلب المالك

| المتطلب | الحالة | الدليل الحالي / الملاحظة |
|---|---|---|
| فصل «طلباتي» للعميل عن إدارة بيانات العملاء | **منفّذ** | `account.html` و`account.js` لطلبات العميل المسجل؛ `customers-dashboard.html` للوحة الإدارة، ونقطة API تفحص الدور. |
| عدم إظهار قاعدة العملاء للزائر/العميل المسجل | **منفّذ ومسنود باختبارات** | واجهات الإدارة تستخدم `requireRoles(..., ['platform_admin'])`، وسجلات النشاط وسيطة خادمية. جداول النشاط RLS مفعّل ولا توجد صلاحية مباشرة للعميل؛ اختبارات رفض الأدوار موجودة. |
| تقسيم لوحة العملاء إلى زوار ومسجلين | **منفّذ** | تبويبا `registered` و`visitors` في `customers-dashboard.html`، مع ترقيم صفحات مستقل وقائمة تفاصيل لكل سجل. |
| هوية الزائر والسلة الحالية | **منفّذ** | `guest_visitors`، و`cart_snapshot` يحوي `productSnapshot` يبنيه الخادم؛ معرّف المتصفح العشوائي لا يصل إلى قاعدة البيانات خامًا. |
| سجل عمليات المشاهدة/البحث/الإضافة/الحذف | **منفّذ** | `customer_product_events` سجل تفصيلي للطرفين؛ ويُدعم ملخص الزائر في `guest_product_analytics`. لا تُحفظ عبارة البحث الخام؛ تسجل المنتجات التي ظهرت في نتائج البحث. |
| الجلسات والمدة وعدد الزيارات | **منفّذ** | `customer_sessions` يسجل البدء وheartbeat والانتهاء و`active_seconds`؛ التحليلات تعرض أعداد الجلسات والمدة ضمن الفترة. مدة النشاط تقريبية عند انقطاع المتصفح فجأة، كما توضّح الواجهة. |
| لوائح الأكثر مشاهدة/بحثًا/إضافةً/حذفًا للزائر | **منفّذ** | `customer_product_ranking`، أربع فئات مرتبة تنازليًا، صفحات محدودة، ولقطات منتج كاملة. |
| نفس اللوائح للعملاء المسجلين | **منفّذ** | تستخدم الأحداث المرتبطة بـ`user_id` وتعرضها في تبويب التحليلات المسجلة. |
| التفاصيل التاريخية الكاملة للمنتج في سجل الفرد | **كان جزئيًا؛ حُسّن الآن** | أصلًا كانت اللقطات الكاملة محفوظة في `product_snapshot` لكن دالة التفاصيل تعيد بناء المنتج من الكتالوج الحي. ترحيل `20261014093223_platform_customer_detail_product_snapshots.sql` أصلح القراءة لتقدّم اللقطة الثابتة للسلة والأحداث وتستخدم joins يسارية كاحتياط. |
| لوحة المتاجر وقاعدة بياناتها «الشاملة في كل شيء» | **موجودة بنطاق تشغيلي جزئي؛ يلزم تعريف الاكتمال** | كيانات قائمة للمتاجر والحسابات والعروض/المنتجات والطلبات والعمولات والشحن والتكاملات/المزامنة والإشعارات. عبارة «كل ما يخصها» أوسع من تعريف قابل للاختبار؛ نحتاج قائمة حقول وتدفقات وصلاحيات من المالك. |
| لوحة إدارة المنصة والتحكم بما يظهر فيها | **منفّذ جزئيًا** | ملخص الطلبات والعملاء والمتاجر في `platform-dashboard.html`؛ إدارة العملاء التفصيلية منفصلة. الأقسام الإدارية المستقبلية لم تحدد بعد. |
| تنظيم الملفات ومعرفة نقطة البدء | **بدأ توثيقه** | هذه الصفحة وخريطة الملفات أدناه تحددان البداية؛ لم تُنقل ملفات التطبيق حتى لا تتعطل مسارات النشر أثناء التدقيق. |

## الفجوات والمخاطر التي يجب متابعتها

1. **اختلاف تاريخ الترحيلات:** سجل Supabase يحوي الإصدارات `20261009230647_harden_order_user_binding` و`20261010001456_guest_browser_identity_analytics` اللذين لا يقابلهما ملف مصدر مستقل في نسخة `main` التي فُحصت؛ كما توجد أسماء ترحيلات لها إصدارات متعددة في السجل الحي. لا تحذف أو تعِد ترقيم تاريخ قديم. الخطوة التالية: تقرير مطابقة نسخة/محتوى ومراجعة مصدر هذه الإصدارات قبل استخدام reset أو نشر دفعة ترحيلات كاملة. الترحيل الجديد موثق محليًا تحت الإصدار الذي سجله Supabase `20261014093223`.
2. **نتيجة مجموعة الاختبارات الكاملة:** `npm test` أنهى 186 اختبارًا وذكر في الملخص 171 نجاحًا و15 فشلًا. السجل المحفوظ يعرض ستة سجلات فشل مفصلة (خمسة ضمن editor وواحد ضمن regression)، لذا لا تتطابق تفاصيل الطرفية الظاهرة مع رقم الملخص؛ أعد التشغيل النظّيف محليًا/على GitHub Actions لجمع تفاصيل كاملة. هذه الإخفاقات الظاهرة ليست ضمن نطاق العملاء.
3. **الاختبارات المخصصة للعملاء:** بعد التغيير نفّذت مجموعة 27 اختبارًا متخصصة في نشاط العملاء والزوار/العملاء المسجلين والسلال والترتيب وصلاحيات الإدارة؛ **27/27 ناجحة**، و`git diff --check` بلا أخطاء.
4. **بيانات الإنتاج قليلة:** معاينة مخطط Supabase وقت الفحص أظهرت قرابة سجل ملف عميل واحد وسجلين للمتاجر و10 منتجات؛ الجداول الخاصة بالنشاط والسلال كانت بلا بيانات أو بأعداد ضئيلة حسب عدادات أداة الجداول. اختبار مباشر لدالة التفاصيل على أحدث زائر أعاد النتيجة الصحيحة لكن بلا سلة/أحداث؛ لذلك لم تتوفر بيانات حية لاختبار صف يحمل لقطة فعلية، ويجب اختبار هذا السيناريو في بيانات تحقق آمنة قبل الإطلاق للمستخدمين.
5. **سياسة الاحتفاظ/الموافقة:** يوجد `consent_at` بمعنى تسجيل وقت، لكنه يملأ تلقائيًا؛ لا توجد في هذا التكليف مدة احتفاظ أو سياسة حذف أو تعريف موافقة صريحة. تُسجّل كقرار مفتوح قبل التسويق/توسيع التتبع، ولا يُفترض أن التصميم الحالي يحسم هذه المسألة.
6. **المستودع عام وفق إعداد GitHub وقت الفحص.** لم يتغير إعداد الخصوصية. راجع قبل أي ملفات جديدة عدم تضمين مفاتيح/بيانات حقيقية؛ الترحيلات والاختبارات الحالية لا ينبغي أن تحتوي أسرارًا.

## ما أُنجز في هذه المهمة

- حفظ نص التكليف الأصلي في `requirements.ar.md` مع تعريف طريقة التعامل معه.
- بناء هذا التدقيق وخريطة الملفات وخطة الأولويات.
- إنشاء ترحيل `20261014093223_platform_customer_detail_product_snapshots.sql` محليًا وتطبيقه على Supabase، مع تحديث صلاحيات الدالة إلى الخادم فقط.
- فحص مباشر أكد: `anon` و`authenticated` لا يملكان صلاحية تنفيذ الدالة، و`service_role` يملكها؛ استدعاء بمعرّف زائر غير موجود يرجع `found=false`.
- تصحيح التعليق القديم في ترحيل رفض وصول العميل إلى بيانات تحليلات الزوار، بعد تأكيد أن الترحيل مطبق في سجل Supabase.
- إضافة اختبار انحدار يغطي استعمال اللقطات الكاملة في السلة والأحداث، بما في ذلك صف المنتج غير المتاح حاليًا.

## ترتيب العمل المقترح لاستمرار المشروع

### المرحلة 1 — تثبيت خط الأساس (الخطوة التالية)

- إعادة تشغيل `npm test` وجمع تفاصيل الإخفاقات كاملة؛ إنشاء بطاقة منفصلة للإخفاقات الأساسية قبل أي تعديل عليها.
- مقارنة قائمة Supabase migration ledger بملفات المستودع واحدًا واحدًا؛ إضافة ملاحظات تاريخية موثّقة للإصدارات المفقودة بدل حذفها أو إعادة ترقيمها.
- اختبار API بصفتين: عميل عادي و`platform_admin`؛ اختبار RLS للقراءة المباشرة؛ إنشاء بيانات fixture في قاعدة اختبار أو معاملة rollback فقط.

### المرحلة 2 — إغلاق تدفق بيانات العملاء

- اختبار أحداث الواجهة الحقيقية للمشاهدة/نتائج البحث/الإضافة/الحذف والتأكد من ربط الـproduct/size/offer الصحيح وعدم ازدواج الحدث.
- إضافة اختبار لقطات المنتج الفعلية إلى دالة التفاصيل والسلال للزائر والعميل، بما فيها منتج مؤرشف/عرض تغير.
- مراجعة تقدير الجلسة والزيارات وحدود القياس؛ اعتماد سياسة الاحتفاظ/الحذف/الموافقة من المالك.
- التأكد أن لوحات العملاء لا تُحمّل إلا بعد نجاح التحقق الإداري، وأن `Cache-Control: no-store` يبقى على واجهات البيانات الخاصة.

### المرحلة 3 — تنظيم الملفات بلا كسر النشر

- إعداد خريطة import/route والـstatic hosting والـrewrites لجميع الملفات المراد نقلها.
- فصل واجهة لوحة العملاء من `platform-dashboard.js` إلى وحدات واضحة مع اختبارات DOM وAPI؛ إبقاء `customers-dashboard.html` وURLs الحالية تعمل.
- نقل APIs إلى مجلدات نطاقية فقط إذا ظل dispatch الحالي قادرًا على خدمة عناوين `/api/...` القديمة.
- تشغيل جميع اختبارات التوافق بعد كل مجموعة نقل صغيرة؛ لا تغيير جماعي للروابط أو rename لملفات كثيرة.

### المرحلة 4 — استكمال المتاجر والمنصة بمتطلبات مالك واضحة

- جرد كل جدول متجر وحقل وتدفق وRole؛ مقارنة الشاشة الفعلية بمصفوفة الاحتياج.
- الاتفاق على ما يظهر في «لوحة المتاجر» وما يظهر في «إدارة المنصة» ومَن يشاهد تفاصيل كل متجر/طلب/عميل.
- توثيق أي «حاجات تانية» جديدة كمتطلبات مؤرخة مع قبول صريح من المالك؛ لا تُخمن حقول أو صلاحيات.

## معيار الإتمام

لا يُعلن اكتمال المشروع حتى تكون كل متطلبات التكليف الأصلية قابلة للربط بجدول/حدث/واجهة/صلاحية واختبار ناجح، مع مطابقة الترحيلات، وثبات فصل «طلباتي» عن لوحة الإدارة، وموافقة المالك على تعريف النطاق المستقبلي للمتاجر والمنصة وسياسة الاحتفاظ بالبيانات.
