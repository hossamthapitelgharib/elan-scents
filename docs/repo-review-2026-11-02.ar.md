## الخلاصة التنفيذية

راجعتُ مخطط Supabase الحي وسجل ترحيلاته ومؤشرات الأمان، ومسارات العميل والضيف والطلبات والمتجر والمنصة ذات الصلة، واختبرت واجهات الحساب والطلبات والإشعارات ولوحة المتاجر. عالجتُ ثلاث فجوات عملية في نسخة العمل: أربعة ترحيلات حيّة كانت بلا ملفات مصدر، وعدم ظهور دفتر عمولات طلبات المتاجر الجديد في لوحة المنصة، واختفاء تفاصيل سلة الطلب والعميل من إشعارات المنصة والمتجر.

النتائج **محلية في مساحة العمل** وليست منشورة: لم أطبّق ترحيلًا أو أكتب سجلًا في Supabase، ولم أرفع commit أو أنشر Worker. فحص قاعدة البيانات كان قراءةً فقط من كتالوج المخطط وسجل الترحيلات ونتائج المستشار الأمني؛ لم أفتح صفوف العملاء أو أستخرج بيانات اتصالهم. لذلك فهذا تدقيق مخطط ومسارات وعزل واختبارات، وليس تدقيقًا يدويًا لكل سجل شخصي في القاعدة.

## ما فُحص

- جرد الملفات والمجلدات واختبارات المشروع وملفات التشغيل والتوثيق؛ تدقيق المسارات المحورية في `api/` و`lib/` وواجهات الحساب والطلبات والبصمة والمتجر والمنصة، وفحص صياغة جميع ملفات JavaScript وMJS المصدرية.
- مراجعة سجل الترحيلات الحي، وجرد 56 جدولًا عامًا وعلاقاتها وRLS، ومؤشرات Supabase الأمنية والأدائية. أُعيد توليد لقطة المخطط من كتالوج PostgreSQL فقط.
- اختبارات اصطناعية لعزل الحسابات والأدوار، وحماية حقول العميل، ونقل الطلب، وإشعارات المتجر، ومطابقة السلة والفاتورة، وعدم كشف الحمولات الخام.

## الإصلاحات التي أُنجزت محليًا

### 1. مزامنة الترحيلات والمخطط

كان سجل Supabase يحتوي 93 ترحيلًا، بينما كان المصدر المحلي يحتوي 89. استُعيدت النصوص الأربعة المفقودة حرفيًا من `supabase_migrations.schema_migrations.statements`، من دون تنفيذها، وأُضيف اختبار SHA-256 يثبت عدم تغيير نصها:

- `20261102074625_store_order_commissions_and_merchant_evidence`
- `20261102074705_order_base_guard_allows_aging_dates`
- `20261102075101_purchase_notice_correction_may_change_amounts`
- `20261102184350_customer_mail_log`

أُضيف rollback للترحيلين اللذين يغيران دالة فقط، وسُجّل استثناء صريح غير قابل للتراجع لحذف دفتر العمولة ولسجل إرسال البريد؛ حذفهما قد يمحو دليلًا ماليًا أو يسمح بتكرار البريد. ينجح مدقق الترحيلات الآن: **93 ترحيلًا، 22 rollback، و71 استثناءً موثقًا**.

كما أُعيد توليد `supabase/schema-snapshot/` من كتالوج Supabase للقراءة فقط. اللقطة الحالية: 56 جدولًا عامًا (كلها RLS مفعّل)، 523 عمودًا، 301 قيد، 105 فهارس غير ناتجة عن قيود، 97 سياسة، 50 trigger، 78 دالة، و12 view. تطابق بصمات الملفات الستة ناتج الاستعلام الحي.

### 2. دفتر عمولات المتاجر

كان قسم «العمولات» في تفاصيل المتجر يقرأ `public.commissions` القديم فقط؛ لم يكن يقرأ `public.store_order_commissions` الجديد. أضفتُ قسمًا منفصلًا باسم «دفتر عمولات طلبات المتاجر» في لوحة المنصة وقراءةً فقط عبر `api/platform-store-detail.js`. المسار يتطلب `platform_admin`، ويُقيد الصفوف بالمتجر المختار، ويعرض حالة العمولة ونسبتها ومبالغها وإثباتها ومراجعتها ورقم التتبع ورقم طلب المتجر، من دون حقول اتصال العميل أو الحمولات الخام. أبقيت قسم العمولات القديمة قائمًا وسمّيته بوضوح حتى لا تختلط الدفاتر.

اختبار API يغطي عزل المتجر والحقول المعروضة. سجل العمولة الحي كان مقدّرًا بصفر صفوف وقت الجرد؛ لذلك ستظهر واجهة فارغة إلى أن تُسجل مبيعات.

### 3. تفاصيل إشعارات الطلب

كان إشعار الانتقال إلى سلة المتجر يخزن الحمولة التفصيلية في قاعدة البيانات، لكن `/api/notifications` كان يعيد العنوان والنص والتاريخ فقط؛ لهذا لم تكن عناصر السلة أو العنوان أو البريد أو رقم طلب المتجر تظهر في الجرس. حدّثت API والواجهة لتعرض بيانات إشعاري `order_initial` و`store_purchase_completed` و`store_purchase_needs_review` لمُدير المنصة وحساب المتجر المرتبط فقط. تظهر بيانات العميل والسلة، رقم التتبع الموحد، رقم طلب المتجر، الإجماليات، حالة المطابقة، والتتبع إن وصل.

الـAPI لا يعيد الحمولة الخام: يبني قائمة حقول مسموح بها، يحدّ عدد البنود والنصوص، ويتجاهل الحقول الإضافية. إشعارات العميل لا تتلقى بطاقة تفاصيل الاتصال والسلة الإدارية. واجهة العرض تهرّب النصوص قبل إدراج HTML. اختبارات مستقلة تثبت عزل الدور والمتجر، والحقول المسموحة، وحدّ البنود، ومقاومة حقن HTML.

### 4. نسخ الأصول

## حالة قاعدة البيانات الحية

- وجدت 56 جدولًا عامًا؛ جميعها مفعّل عليها RLS حسب وصف المخطط. وجود RLS لا يغني عن مراجعة كل منحة وسياسة ودالة؛ اللقطة الجديدة توثق هذه العناصر.
- قدّر جرد المخطط قرابة 12 صفًا في `guest_fingerprints` وصفًا واحدًا في `guest_identity_links`، و6 تحويلات زوار، و52 زائرًا؛ هذه أرقام metadata تقريبية وليست `COUNT(*)` ولا تكفي لقياس دقة مطابقة الهوية. قُدّر سجل العمولة الجديد وسجل البريد بصفر صفوف.
- قاعدة المشروع لديها مهام مجدولة لتنظيف بصمات الزوار بعد 400 يوم، وعمليات البحث، ومفاتيح idempotency؛ وليست كل الجداول التي بلا سياسة مفقودة التنظيف أو الوصول.
- لم أغيّر إعداد Auth أو الصلاحيات أو أي صف في الإنتاج.

## تنبيهات متبقية

### أولوية عالية / تتطلب قرارًا تشغيليًا أو تجاريًا

1. **التسوية المالية غير مكتملة.** دفتر العمولة الجديد يسجل `accrued` أو `voided`، لكنه لا يقدم دورة تسوية أو دفعات أو مرجع تحويل أو إثبات دفع أو حالة `paid`. الدالة الإدارية `platform_review_commission` وملخصات `platform_commission_watch` و`platform_store_order_health` موجودة في قاعدة البيانات، لكنها غير موصولة بمسارات API وواجهة الإدارة. الإضافة التي أُنجزت هنا للعرض فقط. كما أن معدل العمولة يُقرأ من `stores.commission_rate` عند تسجيل العمولة أول مرة؛ لا ينبغي بدء التسوية قبل اعتماد نسبة المتجر وقاعدة المرتجعات والتعديلات وتوقيت الاستحقاق من المالك.
2. **إرسال البريد غير موصول.** ترحيل `customer_mail_log` يوثق في تعليقاته مرسل Worker باسم `api/customer-mail.js` ودوال حجز/إطلاق تمنع التكرار، لكن هذا الملف غير موجود في `api/` ولا يوجد مسار إرسال موصول به. سجل البريد فارغ في التقدير. بالتالي لا أعتبر رسائل الترحيب/الخروج أو بريد المنصة عند التسجيل مكتملة لمجرد وجود جدول الحجز. اختيار مزود الإرسال والأسرار والرسائل وتفعيل المهمة يحتاج قرارًا وإعدادًا منفصلًا.
3. **حدود المعدل على Worker ليست مشتركة تلقائيًا.** `lib/rate-limit.js` يستخدم عداد الذاكرة لكل process/isolate عند غياب مخزن الحالة المشترك أو تعذره. وثائق Cloudflare في المستودع تحذر من ذلك صراحةً. يجب التحقق من إعداد `STATE_STORE_URL` و`STATE_STORE_TOKEN` في الإنتاج، وتفعيل `STATE_STORE_REQUIRED=1` عند اعتماد مخزن مشترك مناسب؛ وإلا يمكن لعدة isolates تجاوز حد الزائر أو الويب هوك بالتوازي. لم أضف خدمة مدفوعة أو أسرارًا.

### أمن وخصوصية

4. مستشار Supabase أظهر **9 جداول RLS مفعّل بلا policy**؛ كثير منها مقصود أن يكون خادميًا فقط، مثل سجل العمليات والربط والعمليات الداخلية. كما أظهر **4 دوال `SECURITY DEFINER` قابلة للتنفيذ من authenticated**: `confirm_store_order_purchase` و`place_store_order` و`replace_customer_cart` و`request_store_order_cancellation`. راجعت حواجز الهوية/المالك في المسارات والدوال والاختبارات المرتبطة، لكن هذه التحذيرات لا تختفي وتستدعي فحصًا دوريًا لكل تغيير. لا تفتح سياسات لهذه الجداول لمجرد إسكات المستشار.
5. إعداد Supabase Auth الخاص بحماية كلمات المرور المسرّبة غير مفعّل حسب التنبيه الحي؛ هذا إعداد لوحة تحكم لا يصلحه تعديل الشيفرة. يظل قرار تفعيله مرتبطًا بالخطة والإعداد.
6. ظهرت **24 فهرسًا غير مستخدم** و**53 نمطًا لسياسات permissive متعددة** في تنبيهات الأداء. هذه ليست برهان ثغرة ولا مبررًا لحذف جماعي؛ يلزم تحليل استعلامات الإنتاج ومراجعة تداخل كل سياسة قبل التنظيف.
7. مطابقة بصمة الزائر تحافظ على نهج متحفظ وتخزن الإشارات خادميًا، لكن وجود عدد قليل من الروابط لا يسمح بإثبات دقة مطابقة الأشخاص أو قياس الإيجابيات الخاطئة. كما أن بعض إشارات النشاط تأتي من المتصفح ويمكن التلاعب بها؛ لا ينبغي تقديم البصمة كهوية يقينية. يلزم قياس عملي مع مجموعة اصطناعية موسومة ومراجعة السلاسل حتى حد المجموعة الحالي، وتأكيد إعداد مخزن الحدود المشتركة قبل الاعتماد على الحماية من الإساءة.

## المطلوب قبل الإغلاق أو النشر

1. مراجعة التغييرات المحلية ورفعها إلى GitHub حتى يتوافق `main` مع سجل الترحيلات الحي؛ لا تزال التغييرات غير ملتزمة وغير منشورة.
2. قرار المالك بشأن نسبة العمولة، متى تُحتسب، وكيف تُسوّى وتُراجع.
3. قرار مزود البريد وإعداد الأسرار والخدمة التي سترسل الرسائل؛ لا تستخدم API عامة لقبول عنوان بريد حر كي لا تتحول إلى مرسل مفتوح.
4. التحقق من إعداد مخزن المعدل المشترك على بيئة Worker الفعلية، ثم تجربة حقيقية بسلة/طلب اصطناعي من دون قراءة بيانات عميل حقيقي.
5. إبقاء تحذير كلمات المرور المسرّبة وقرارات إعداد Auth ضمن قائمة تشغيل المالك.

**حدّ التنفيذ:** لا commit، لا push، لا نشر، ولا كتابة في قاعدة Supabase الحية. كل ما تغير في هذه الجولة محفوظ في نسخة العمل المحلية فقط.
