## المنفذ

### 1. أسرار Worker وسجلاته

تحققت قراءةً من إعداد Worker الحي بعد التحويل: `GITHUB_TOKEN` و`SUPABASE_SERVICE_ROLE_KEY` أصبحا `secret_text`، و`redact_query_string=true`. لم أقرأ أو أُظهر أي قيمة سرية. هذا يحمي الإعدادات والسجلات من العرض كنص عادي، **لكنه لا يدوّر القيم القديمة**.

**إجراء أمني ما زال مطلوبًا:** دوّر GitHub token إلى token محدود بالمستودع وصلاحية Contents اللازمة فقط، ودوّر `SUPABASE_SERVICE_ROLE_KEY` من Supabase ثم حدّث Cloudflare Secret. تعريضهما السابق كـ`plain_text` يعني أن تغيير نوع binding وحده ليس دليلًا كافيًا على أن القيم القديمة لم تُنسخ أو تُلتقط.

### 2. حد معدل مركزي وفشل مغلق

أضيف العداد الذري `public.consume_edge_rate_limit` والجدول الخاص `private.edge_rate_limit_buckets` في ترحيل Supabase رقم `20261102201001` المسجل في القاعدة (94 ترحيلًا). يرسل Worker مفتاح HMAC ذي 256 بت مشتقًا من المسار/العميل/النافذة؛ لا يُحفظ عنوان IP الخام. دالة العداد محصورة في `service_role`، والجدول لا يملك `anon` أو `authenticated` أو `service_role` منحًا مباشرة. يجري تنظيفًا محدودًا للمنتهية حتى 500 صف عند عينة من المفاتيح.

أصبح `STATE_STORE_REQUIRED=1` إلزاميًا في إعداد Worker، فيُرفض الطلب المحمي عند تعذر المخزن بدل الرجوع إلى عداد محلي لكل isolate. إعداد smoke test المحلي فقط يعطّل هذا الإلزام لأنه يستخدم مفاتيح Supabase وهمية. كل فحص موزع يضيف استدعاء REST داخليًا إلى Supabase؛ راقب حدود الحصة ومعدل الطلبات. عودة Supabase بمعدل محدود تؤدي إلى الرفض المؤقت (fail-closed)، لا تجاوز الحماية. أُضيف حد إلغاء زمني 3 ثوانٍ للطلبات إلى المخزن.

اختُبر نص الترحيل في معاملة أُلغيت قبل تطبيقه. وبعد التطبيق شُغّل `tests/shared-rate-limit.sql` داخل `BEGIN/ROLLBACK`: نجح عدّ الزيارتين المتسلسل، وفحص TTL والمنح، ثم تأكدت قراءة مستقلة أن صف الاختبار غير موجود.

### 3. تعليق Turnstile

أزيل انتظار `turnstile.ready()` غير المحدود، وأضيفت مهلة تحميل وتنظيف وإعادة محاولة، وحد حلّ أقصى ورسالة خطأ، مع منع إرسال كلمة المرور عند فشل التحقق. أضيف اختبار انحدار يغطي `ready()` غير المستجيب، ثم زِيد رقم الأصول إلى `20261102-10`. **لم يُفعّل Turnstile**: بقي مفتاح الموقع فارغًا ولم يُختبر الصندوق الحقيقي على هاتف المالك، لذا لا تُعد حماية CAPTCHA الإنتاجية مكتملة.

## غير محسوم — لا أصفه بأنه مُغلق

1. **تدوير السرّين:** يلزم تدوير GitHub token ومفتاح Supabase service-role كما سبق؛ نوع Secret الجديد لا يبطل النسخ القديمة المحتملة.
2. **كلمات المرور المسرّبة:** ما زال تحذير Supabase Auth قائمًا. تغيير هذا الخيار يتبع خطة Supabase وإعداد Auth، وليس ترحيل SQL أو حماية في الواجهة.
3. **اختبار Turnstile الواقعي:** جرّب التسجيل والدخول واستعادة كلمة المرور على هاتف حقيقي، ثم فعّل CAPTCHA في Supabase بالـsecret من لوحة المفاتيح؛ لا تضع الـsecret في Git.
4. **تسوية عمولة المتاجر:** الدفتر الحالي يسجل الاستحقاق/الإبطال، لكنه لا ينفذ دفعات أو إثبات تحويل أو حالة `paid`. يلزم اعتماد النسبة، المرتجعات/التعديلات، توقيت الاستحقاق وطريقة الدفع قبل بناء دورة تسوية؛ لا يجوز اختراعها تقنيًا.
5. **بريد المنصة:** حجز/منع التكرار موجود في قاعدة البيانات، لكن خدمة الإرسال وموفر البريد لم يُوصلا.
6. **فحوص SECURITY DEFINER:** الأربعة تحذيرات الحالية تخص دوال طلبات، ولا ينبغي إلغاء صلاحياتها عشوائيًا؛ يجب اختبار تدفقات حساب العميل كاملة إذا تقرر تعديلها.
