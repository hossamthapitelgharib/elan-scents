# تقرير ربط فلاتر الكتالوج بقاعدة البيانات بعد التراجع

**المشروع:** `elan-scents`
**التاريخ:** 2026-11-05
**الحالة المرجعية للكود:** `main` عند commit `6adf836`
**مشروع Supabase:** `sbgdtuqfrnfeggkwqtrw`
**نطاق التقرير:** مراجعة قراءة فقط بعد التراجع عن تنفيذ توحيد فلاتر الجنس؛ لا يطبق هذا التقرير أي تغيير على الكود أو قاعدة البيانات.

## 1. ملخص تنفيذي

أُعيدت قاعدة البيانات والمستودع إلى الحالة السابقة لتنفيذ توحيد فلاتر الجنس. لم يعد جدول `categories` يحتوي على عمود إضافي خاص بالتصنيف، ولم يعد هناك فهرس مخصص أُنشئ في التنفيذ المتراجع عنه. كما عادت سياسة القراءة العامة في `categories` إلى `using (true)`.

الوضع الحالي يحتوي على تمثيلين متداخلين للجنس:

- `products.gender`، وهو خاصية مباشرة للمنتج، وقيمه المسموحة `men` و`women` و`unisex`.
- ثلاثة سجلات في `categories` بأسماء «رجالي» و«نسائي» و«عطر يجمعنا»، مع روابط في `product_categories`.

هذا التكرار لا ينبغي معالجته بإضافة وسم مؤقت أو عمود جديد. التصميم الآمن هو اعتماد `products.gender` كمصدر وحيد للجنس، مع إبقاء قرار إزالة سجلات الجنس القديمة من `categories` مرحلة مستقلة تسبقها عملية تدقيق للروابط والاستخدامات.

أما المناسبات والنوتات فلهما تصميم علائقي مناسب موجود أصلًا، ولا يحتاجان إلى نسخ أو دمج داخل `categories` أو `products`:

```text
products
  ├── product_occasions → occasions
  └── product_notes    → aromatic_notes
```

## 2. الحالة الحالية لجدول `categories`

الأعمدة الحالية:

| العمود | النوع | القاعدة |
|---|---|---|
| `id` | `uuid` | مفتاح أساسي، `gen_random_uuid()` |
| `name` | `text` | إجباري وفريد |
| `image_url` | `text` | اختياري |
| `created_at` | `timestamptz` | إجباري، `now()` |
| `updated_at` | `timestamptz` | إجباري، `now()` |

الفهارس والقيود:

```text
categories_pkey
categories_name_key UNIQUE(name)
```

سياسات الوصول الحالية:

```text
admin_all
public_read USING (true)
```

السجلات الحالية التي تمثل الجنس:

| الاسم | عدد المنتجات المرتبطة |
|---|---:|
| رجالي | 7 |
| نسائي | 6 |
| عطر يجمعنا | 4 |

هذه السجلات لم تُحذف أثناء التراجع، لأن حذفها دون تدقيق قد يترك روابط يتيمة أو يكسر واجهات تعتمد عليها.

## 3. الحالة الحالية لجدول `products`

الأعمدة المهمة للفلاتر:

| العمود | النوع | الحالة |
|---|---|---|
| `id` | `uuid` | مفتاح أساسي |
| `brand_id` | `uuid` | مفتاح خارجي إلى `brands` |
| `name` | `text` | إجباري |
| `slug` | `text` | إجباري وفريد |
| `gender` | `text` | اختياري حاليًا |
| `status` | `text` | `draft` أو `published` أو `archived` |
| `is_active` | `boolean` | إجباري، افتراضيًا `true` |

قيد الجنس الحالي:

```sql
CHECK (gender IN ('men', 'women', 'unisex'))
```

والقيمة `NULL` ما زالت ممكنة لأن العمود اختياري. لذلك لا يجوز جعل الفلتر يفترض أن كل منتج لديه gender قبل تنفيذ تدقيق بيانات مستقل.

التوزيع الحالي:

| قيمة `gender` | عدد المنتجات |
|---|---:|
| `men` | 5 |
| `women` | 3 |
| `unisex` | 2 |

سياسة القراءة العامة للمنتجات لا تعرض إلا المنتج المنشور والنشط والمتاح وفق `private.product_is_available(id)`.

## 4. جداول المناسبات والنوتات الموجودة

الجداول الحالية هي:

```text
occasions
product_occasions
aromatic_notes
product_notes
```

أعمدة الجداول الوسيطة:

```text
product_occasions(product_id, occasion_id, created_at, updated_at)
product_notes(product_id, note_id, created_at, updated_at)
```

السجلات المتوقعة التي يجب ربط أيقوناتها بالسجلات الحقيقية هي:

### المناسبات الخمس

```text
عمل
ليلي
موعد
نهاري
هدية
```

### النوتات الخمس

```text
حمضي
خشبي
عنبري
عود
هيل
```

يجب التحقق من أسماء هذه السجلات و`id` الفعلي لها قبل كتابة أي كود أو ترحيل. لا يجوز افتراض أن ترتيب الصفوف ثابت أو أن السجل رقم 0/1/2 هو دائمًا المناسبة نفسها.

## 5. القرار المعماري المقترح

### 5.1 الجنس: مصدر واحد فقط

يُعتمد:

```text
products.gender
```

ولا يُستخدم:

```text
categories
product_categories
```

لتمثيل الجنس في الفلاتر الجديدة.

الربط المنطقي:

```text
فلتر رجالي  → products.gender = 'men'
فلتر نسائي  → products.gender = 'women'
فلتر يجمعنا → products.gender = 'unisex'
```

السبب: الجنس خاصية مباشرة للمنتج، بينما `categories` جدول علاقات متعدد القيم. استخدام الاثنين معًا يخلق مصدرين للحقيقة واحتمال اختلاف النتائج.

### 5.2 `categories`: تصنيفات موضوعية فقط مستقبلًا

يبقى جدول `categories` متاحًا لتصنيفات مستقلة فعلية، مثل:

```text
شرقي
زهري
فاخر
صيفي
اقتصادي
```

لكن لا تُضاف إليه فئات الجنس بعد اعتماد `products.gender`.

إزالة سجلات الجنس القديمة لا تتم في نفس ترحيل ربط الفلاتر. تسبقها عملية تدقيق تقارن:

```text
product_categories.name
products.gender
```

وتبحث عن:

- روابط غير متطابقة.
- منتجات بلا gender.
- منتجات مرتبطة بأكثر من تصنيف جنس.
- استخدامات الواجهة أو التقارير لهذه السجلات.
- أي بيانات منشورة تعتمد على `category_id` القديم.

بعد مراجعة التقرير فقط، يمكن إنشاء ترحيل مستقل لإزالة روابط الجنس القديمة ثم حذف السجلات إن ثبت عدم الحاجة إليها، مع نسخة تراجع واختبار قبل الإنتاج.

### 5.3 المناسبات والنوتات: جداول علاقات حقيقية

لا تُنقل المناسبات أو النوتات إلى أعمدة نصية في `products`، ولا تُكرر في `categories`.

يُستخدم:

```text
occasions.id
product_occasions.occasion_id
aromatic_notes.id
product_notes.note_id
```

وإذا احتجنا إلى مفاتيح مستقرة للواجهة، يضاف `slug` فريد إلى الجدولين في ترحيل منفصل، مع تعبئة السجلات الحالية فقط وقيد `UNIQUE` ونسخة تراجع.

## 6. ربط الأيقونات والفلاتر

القاعدة الأساسية:

> الأيقونة لا ترتبط بترتيب مصفوفة أو رقم موضعي؛ ترتبط بسجل قاعدة البيانات نفسه.

التدفق المقترح:

```text
تحميل occasions أو aromatic_notes
  ↓
قراءة id وname وimage_url أو slug
  ↓
إنشاء بطاقة/أيقونة الفلتر مع data-id حقيقي
  ↓
إرسال id إلى طبقة الاستعلام
  ↓
التصفية عبر جدول الربط
```

ممنوع الاعتماد على أن:

```javascript
options[0] === 'عمل'
options[1] === 'ليلي'
```

بدلًا من ذلك يجب أن يكون الخيار مرتبطًا بـ`occasion_id` أو `note_id` الحقيقي، وأن يبقى صحيحًا حتى لو تغير ترتيب السجلات.

## 7. شروط عرض النتائج

أي فلتر يجب أن يعيد منتجات مرتبطة فعليًا بعروض متاجر قابلة للعرض، لا مجرد منتجات لها علاقة بجدول مناسبة أو نوتة.

التسلسل المنطقي:

```text
product
  → product_sizes
  → store_products
  → store
```

ويُطبق نفس شرط الإتاحة المعتمد في الكتالوج العام، دون اختراع شرط مختلف داخل الواجهة. يجب أن تتوافق النتائج مع:

```text
published product
active product
available store offer
```

ويجب تنفيذ التصفية الأساسية في مصدر البيانات/الاستعلام، لا تحميل كل المنتجات ثم الاعتماد على JavaScript وحده لإخفائها.

## 8. سلوك الفلاتر المتعددة

إذا اختار العميل:

```text
رجالي + هدية + عود
```

فالمطلوب هو التقاطع:

```sql
products.gender = 'men'
AND EXISTS (
  select 1
  from product_occasions po
  where po.product_id = products.id
    and po.occasion_id = :occasion_id
)
AND EXISTS (
  select 1
  from product_notes pn
  where pn.product_id = products.id
    and pn.note_id = :note_id
)
AND product is published, active, and available
```

لا ينبغي دمج النتائج باتحاد `OR`، ولا استخدام أسماء العرض العربية كمعرفات داخل الاستعلام.

## 9. خطة التنفيذ المرحلية الآمنة

### المرحلة الأولى: تدقيق قراءة فقط

1. جلب كل سجلات `categories` الثلاثة وروابطها.
2. مقارنة كل رابط مع `products.gender`.
3. جلب سجلات المناسبات والنوتات مع `id` و`name` و`image_url`.
4. التأكد من وجود خمس مناسبات وخمس نوتات وعدم وجود تكرار اسمي.
5. حصر المنتجات التي تحتوي `gender IS NULL`.
6. حصر المنتجات التي لا ترتبط بعرض متجر متاح.

### المرحلة الثانية: تعديل الكود فقط

1. جعل `products.gender` مصدر فلتر الجنس.
2. قراءة المناسبات والنوتات من الجداول الحالية.
3. استخدام `id` الفعلي في `data-*` وطلبات الفلترة.
4. عدم تغيير مخطط قاعدة البيانات في هذه المرحلة.
5. إضافة اختبارات للعناصر الخمسة ولتغير ترتيب السجلات.

### المرحلة الثالثة: ترحيل اختياري للمفاتيح المستقرة

إذا ثبتت الحاجة، يضاف `slug` فريد إلى `occasions` و`aromatic_notes` فقط، دون تغيير أسماء السجلات أو حذف البيانات.

### المرحلة الرابعة: تنظيف التكرار

بعد تقرير التدقيق وموافقة المالك:

1. إزالة روابط `product_categories` الخاصة بالجنس فقط.
2. التحقق من عدم وجود روابط يتيمة.
3. حذف سجلات الجنس القديمة فقط إذا ثبت عدم استخدامها.
4. إبقاء نسخة تراجع مستقلة.
5. تشغيل اختبارات RLS والكتالوج قبل وبعد الترحيل.

## 10. ضوابط منع الخطأ

- عدم إنشاء عمود `category_type` أو وسم بديل لمعالجة مشكلة المصدرين.
- عدم حذف سجلات من الإنتاج ضمن ترحيل الفلاتر الأول.
- عدم تغيير `products.gender` تلقائيًا اعتمادًا على اسم category دون تقرير فروقات.
- عدم الاعتماد على ترتيب UUID أو ترتيب الصفوف.
- عدم استخدام الاسم العربي كمعرف داخلي.
- عدم تغيير سياسة RLS القائمة دون سبب مستقل ومراجعة أمنية.
- كل ترحيل يجب أن يملك ملف rollback أو توثيقًا صريحًا لعدم قابليته للعكس.
- تشغيل `npm run check:migrations` والاختبارات قبل التطبيق.
- تطبيق قاعدة البيانات بعد مراجعة نص الترحيل، ثم التحقق من `list_migrations` ونتائج SQL.

## 12. الخلاصة

التصميم الأنسب هو:

```text
الجنس       → products.gender
التصنيفات   → categories / product_categories للتصنيفات غير الجنسية فقط
المناسبات   → occasions / product_occasions
النوتات     → aromatic_notes / product_notes
الأيقونات   → IDs أو slugs حقيقية من قاعدة البيانات
التوفر      → نفس شروط كتالوج المتجر العامة
```

بهذا يصبح لكل نوع فلتر مصدر واحد واضح، ولا تُكرر السجلات بين جدولين، ولا تعتمد الواجهة على ترتيب مؤقت أو قيمة نصية قابلة للتغيير.
