# اختبارات Élan Scents

تشمل `regression.test.js` اختبارات الانحدار التي أُجريت أثناء بناء تدفقات الطلبات واللوحات:

- سلامة JavaScript وروابط القائمة.
- ربط «طلباتي» بـ `/account.html`.
- إنشاء عملية شراء موحدة وتقسيمها حسب المتجر.
- اشتراط تسجيل الدخول وإنشاء رقم التتبع.
- استقبال إشعارات المتجر ومطابقة الطلب.
- إشعار الإتمام الناجح.
- إلغاء الطلب وإصدار رمز الاسترجاع.
- استرجاع المنتجات مع اختبار عدم التكرار.
- صلاحيات لوحة العميل والمتجر والمنصة وعزل البيانات.
- تحديث حالات طلب المتجر.
- مركز الإشعارات ووسم الإشعار كمقروء.
- الحفاظ على هوية السلة السابقة على الهاتف.
- اختزال واجهة «طلباتي» إلى الطلبات الحالية وآخر الطلبات والأرشيف القابل للبحث.
- سلامة API البحث حسب رقم التتبع والسنة وعزل البيانات الداخلية.

## التشغيل محليًا

```bash
npm test
```

يُنشئ `npm test` تقريرًا زمنيًا في `reports/test-runs/` حتى عند فشل الاختبارات. أما `npm run test:raw` فيشغّل Node Test Runner دون إنشاء تقرير.

## التشغيل التلقائي

يعمل workflow الموجود في `.github/workflows/tests.yml` تلقائيًا عند كل `push` إلى أي فرع وعند كل Pull Request إلى `main`.

بعد كل تشغيل عبر GitHub Actions يرفع مجلد `reports/test-runs/` كـArtifact لمدة 30 يومًا، بما في ذلك التشغيل الفاشل. التشغيل المحلي عبر `npm test` يحفظ التقرير في مساحة العمل؛ يصبح رفعه البعيد تلقائيًا عند push/فتح Pull Request يشغّل الـworkflow، ولا ينفذ السكربت push للـGit من تلقاء نفسه.

## قاعدة مهمة

أي اختبار JavaScript جديد يجب إضافته إلى `tests/regression.test.js` أو ملف `.test.js` ثم تشغيل `npm test` قبل الرفع. لا تُحفظ بيانات العملاء أو كلمات المرور أو مفاتيح Supabase داخل الاختبارات؛ اختبارات JavaScript تستخدم بيانات وهمية ومحاكاة للـAPI.

اختبار Supabase التكاملـي الموجود في `tests/customer-activity-transactional.test.sql` يتحقق من حفظ أحداث الزوار والعملاء المسجلين، الجلسات والسلال ولقطات المنتجات وعروض الأحداث المنفصلة، ونص كل عملية بحث ونتائجها (بما فيها البحث بلا نتائج)، ونقل سجل الزائر عند تسجيله، وحذف البحث بعمر 366 يومًا مع الإبقاء على سجل بعمر 364 يومًا، وبقاء لقطات الحدث والترتيب ونتيجة البحث بعد حذف منتج/حجم/عرض/صورة اصطناعية. يُشغّل على قاعدة Supabase فقط عند الحاجة، منفصلًا عن GitHub Actions: يحيط الكتابات الاصطناعية بـ`BEGIN ... ROLLBACK` ويستخدم استثناءً داخليًا لإرجاع صفوف fixture والتحقق من اختفائها. لا يقرأ سجلات العملاء الحقيقية، ولا يرسل بريدًا أو يستدعي Auth API. لا تُشغّل اختبارات قاعدة البيانات على الإنتاج بلا آلية rollback واضحة، ولا تُضف مفاتيح قاعدة البيانات إلى CI؛ التشغيل الآلي يحتاج فرع/مشروع اختبار مخصصًا وأسرارًا معتمدة.
