## ما يمكن استعادته وما لا يمكن إثباته

توجد نسخ محلية/تاريخية بأسماء إصدارات مختلفة، وهي مطابقة بايتًا ببايت للملفين اللاحقين الحاليين:

- `20261010021000_harden_order_user_binding.sql` (blob يبدأ `3d9ae1ae`) يطابق `20261010014304_harden_order_user_binding.sql`.
- `20261010030000_guest_browser_identity_analytics.sql` (blob يبدأ `caff97e4`) يطابق `20261010014327_guest_browser_identity_analytics.sql`.

هذه الأدلة تثبت محتوى النظيرين الموجودين، لكنها **لا تثبت** أن البايتات نفسها طُبقت تحت رقمي Supabase الأقدمين. لا توجد قرينة Git تربط مصدرًا بعينه بالإصدارين الأقدمين. لذا لا يجوز إنشاء ملفات قديمة بأسماءهما أو الادعاء أنها الأصل، ولا تعديل جدول migration history يدويًا.

## الإجراء الآمن

1. إبقاء فجوة المصدر معلّمة كما هي في دليل Supabase.
2. عدم إضافة migration بأثر رجعي أو إسقاط/إعادة تطبيق schema لمجرد ملء الاسم.
3. إذا قدم المالك backup/export رسميًا من سجل SQL أو نسخة موثوقة من المصدر، يُحفظ دليلها وتُراجع مطابقتها مع المخطط الحي قبل أي reconciliation.
4. تستمر أي تغييرات مستقبلية بإصدارات جديدة فريدة، مع مطابقة رقم الملف بالرقم الذي يسجله Supabase بعد التطبيق.

هذا إغلاق للتحقيق وعدم التخمين، وليس ادعاءً بأن مصدرَي الإصدارين القديمين قد استُعيدا.
