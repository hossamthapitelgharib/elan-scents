# Live schema snapshot

A read-only, structure-only snapshot of the live Supabase project (`public` schema plus the pieces of `private`, `auth`, `storage`, `cron` and the realtime publication that the storefront depends on). It exists because the base schema predates `supabase/migrations/`, so the migrations alone cannot describe the database.

It is **documentation for people and agents, not a restore script**. It does not contain row data, secrets, function bodies or `CREATE` statements you can run. Use it to answer "what does the live database look like right now" and to spot drift.

- Taken: 2026-11-02, read-only, from the live PostgreSQL 17 database after migration `20261102184350` (`customer_mail_log`). The ledger held 93 records. All six snapshot files were regenerated from `generate.sql` and their md5 values match the live query output. The two public tables added since the previous snapshot are `store_order_commissions` and `customer_mail_log`; the newer functions, views, policies and triggers are included in the regenerated files.
- Generated by `generate.sql` in this folder. It reads system catalogs and the migration version list only.
- Text is plain ASCII. Each file is the generated text followed by exactly one newline.

## What is in it

- 56 tables in `public`, all with row level security on (none forced), 523 columns, 301 constraints (primary, unique, foreign key, check), 105 indexes that are not constraints, 97 policies, 50 triggers and 7 column-level grant groups.
- 78 functions, 72 of them `SECURITY DEFINER`. Each line carries the language, volatility, `search_path`, owner, who can execute it, and the md5 of `pg_get_functiondef`. A changed function body therefore shows up as a changed line without the body being copied here.
- 12 views with their grants, column list and an md5 of the definition.

Table block layout:

```
TABLE <name>  rls=on  grants: anon=<privs> authenticated=<privs> service_role=<privs>
  <column> <type> [NOT NULL] [DEFAULT <expr>]
  CONSTRAINT <name> <definition>
  CREATE INDEX ...
  COLUMN GRANTS <role>=<privilege>,...: <columns>
  POLICY <name> PERMISSIVE|RESTRICTIVE FOR <cmd> TO <roles> USING (...) WITH CHECK (...)
  CREATE TRIGGER ...
```

Privilege letters: `r` select, `a` insert, `w` update, `d` delete, `D` truncate, `x` references, `t` trigger, `-` none. Blocks are separated by one blank line and sorted by table name.

## Reading it

- Table grants vary by purpose: some public catalog tables grant `SELECT` and rely on RLS, while sensitive customer/order/financial tables are server-only or tightly scoped. Inspect the per-table `grants`, policies and column grants in the snapshot; do not infer isolation from RLS being enabled alone.
- The default privileges for new objects in `public` still grant `anon` and `authenticated` access (see `DEFAULT PRIVILEGES` in `misc.txt`). A new table or function therefore needs explicit `revoke` statements in its migration, as the existing migrations do.
- `exec=` on a function line lists who may execute it: `PUBLIC` means everyone, otherwise the named roles.

## Checking for drift

1. Run `generate.sql` against the live project (read-only; the Supabase SQL editor or any SQL client works).
2. Compare the `md5` column with the table above, and the `ledger` row (`<count> latest <version>`) with `supabase_migrations.schema_migrations`.
3. If a row differs, the live database changed after this snapshot. Find the matching migration, regenerate the affected file(s) from the `txt` column (write `txt` plus one newline), update the md5 in the table above in the same commit, and run `npm test`.

Applying a migration to the live project without updating this snapshot is not an error, but the next person to run the drift check will see it. Whoever applies a migration that changes tables, policies, grants, functions or cron jobs should refresh the affected file in the same change when they can.
